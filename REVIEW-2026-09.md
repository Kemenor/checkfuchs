### 1. `ViewRepository._toTask` drops the `windowBands` column (normal)

Every Task that reaches `watchViewState`, `watchLensTasks` or `_assemble`
has `bands == null`. The sibling `TaskRepository._toTask`
(`task_repository.dart:492`) rehydrates them with
`bands: bandsFromSql(r.windowBands)`; the View-side mapper is missing that
line and does not even import `converters.dart`.

`phaseOf` in `lib/domain/task.dart` only returns Pending during a band gap
when `bands` is non-null, so a "morning or evening" MultiSlice habit shows as
ready-to-check all afternoon. `projectLens`'s first-pending filter, stats and
window classification are affected the same way.

**Fix:** import `../db/converters.dart` and add
`bands: bandsFromSql(r.windowBands)` to the mapper, or extract one shared
row-to-Task function used by both repositories.

### 2. `_nextTransition` ignores MultiSlice band boundaries (nit)

`_nextTransition` (`view_repository.dart:472-495`) only feeds
`m.task.start` and `m.task.end` into `consider(...)`. For a task with bands
(morning 6-12 + evening 18-24) the earliest candidate is the envelope end, so
`viewStateProvider` (`lib/providers.dart:76-91`) arms no timer for the 12:00
Active→Pending flip. Between 12:00 and 18:00 the UI keeps rendering the task
as Active while `completeTask` reads a fresh `now`, `canComplete` returns
false, and the tap is silently discarded (`task_repository.dart:205`).

Independent of #1: fixing #1 exposes this, since bands then exist on the
View side.

**Fix:** also `consider(...)` each band's start and end for open members.

### 3. `seedDefaults` persists hardcoded English "Home" and "Default" (nit)

`view_repository.dart:141` inserts `name: 'Default'` and `:148` inserts
`name: 'Home'`. `home_shell.dart:172` renders the view name as the
bottom-nav label, so de/fr/it users get an English tab on first run, and
since the names are stored in the DB a later language switch cannot fix it.
Violates the CLAUDE.md "no hardcoded user-facing strings" rule.

**Fix:** pass `AppLocalizations` into the seed and use l10n keys
(e.g. `seedViewHome`, `seedLensDefault`), or store a slug and render it
through l10n.

### 4. Demo loader hardcodes "Home" (nit)

`demo_data.dart:53` seeds `view('Home', 'home', 0)` while the adjacent seeds
use `l10n.demoViewHabits` / `l10n.demoViewLongterm`. Store screenshots in
de/fr/it would show an English "Home" tab next to translated neighbours.
No `demoViewHome` key exists in the arb files yet.

**Fix:** add `demoViewHome` to all four arb files and use it. Sweep together
with #3.

### 5. `stopRepeating` runs update + delete without a transaction (nit)

`task_repository.dart:347-351` awaits an update (null `templateId` on the
children) then a delete (drop the template) with no `db.transaction(...)`,
unlike every other multi-step write on the class (`createTemplate`,
`deleteTemplate`, `turnIntoSeries`, `pauseTemplate`, `setTemplateLenses`).
A `reconcileAll` between the two awaits (timer, background refresh, or any
swipe) sees a template with no children, materialises a fresh instance, and
the delete then fails the `Tasks.templateId` FK (no `onDelete`,
`database.dart:61`), leaving the children detached and the template alive.

**Fix:** wrap both writes in `db.transaction(() async { ... })`.

### 6. `correctMissedTask` doc comment copied from `skipTask` (nit)

`task_repository.dart:211-212` reads "Swipe Skip — declines this instance,
then reconciles." above `correctMissedTask`, which is neither Skip nor
reconciling. Only the second line ("Missed → Done on a habit instance") is
correct.

**Fix:** delete the first line here; it belongs above `skipTask` (line 227).

### 1. Empty Due tile on a future-start one-off crashes `showDatePicker` (normal)

In `_editWindowDate` (`task_detail_sheet.dart:183-199`) with `isEnd == true`
and `_task.end == null`: `oldDay` is null, so `first` becomes
`_task.start ?? today` (line 188) while `initialDate` stays `oldDay ?? today`
(line 193). The clamp on line 190 short-circuits on `oldDay != null`. For a
task with a future start (e.g. start 2026-09-15, end null) `first` is
2026-09-15 and `initialDate` is today, so `showDatePicker` asserts
`!initialDate.isBefore(firstDate)` and throws.

The tile renders for every non-recurring open task (line 437,
`!recurring && _task.isOpen`), which includes `TaskPhase.pending` — the
natural state of a task created with "Starts: tomorrow" and no due date.

**Fix:** clamp `initialDate` to at least `first`, e.g.
`initialDate: (oldDay ?? today).isBefore(first) ? first : (oldDay ?? today)`.

### 2. `sync()` calls `cancelAll()` and wipes delivered notifications (normal)

`notification_scheduler.dart:196` issues `_plugin.cancelAll()` before
rescheduling. In flutter_local_notifications `cancelAll` removes pending
schedules **and** already-presented notifications (Android: active
notifications; iOS: `removeAllDeliveredNotifications`).
`notificationSyncProvider` (`providers.dart:104-119`) re-runs `sync()` on
every `tasksProvider` emission — create, complete, rename, and
`fireImmediately` at app open — so any reminder that already fired and is
still undismissed in the tray is silently wiped by the next unrelated DB
write. Example: the 09:00 "Take pills" reminder fires during a meeting; at
09:15 the user checks off any other task and the banner disappears before
they acted on it.

The comment on line 17 ("completing/skipping/editing instantly cancels the
affected pings") describes per-task cancellation, not a blanket clear.

**Fix:** cancel only pending requests (`pendingNotificationRequests()` →
`cancel(id)` per entry), or diff the desired set against the pending set and
cancel/schedule by id.

### 3. iOS notification permission is never requested (normal)

`NotificationScheduler.notificationsEnabled()`
(`notification_scheduler.dart:103-115`) only queries
`resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()`,
which is null on iOS, so the method returns null.
`ensureNotificationPermission` (`providers.dart:131-137`) then hits
`if (enabled != false) return;` — `null != false` is true, so
`requestPermission()` never runs. Combined with the deliberate
`requestAlertPermission: false` at init (`notification_scheduler.dart:57-60`),
iOS users saving their first reminder never see the OS dialog and every
subsequent `zonedSchedule` is dropped by iOS. Reminders never fire on iOS
unless the user enables them manually in system Settings.

**Fix:** also probe iOS via
`IOSFlutterLocalNotificationsPlugin.checkPermissions()`, or gate on
`enabled == true` and always attempt the request otherwise.

### 4. `datedWindow` can return `end < start` for a future start date (normal)

`_save()` in `create_task_sheet.dart:142` calls
`_window.datedWindow(now, _startDate, _dueDate)`. The Start row's date picker
accepts any date from today onward, so `_startDate` can be days in the
future while `_dueDate` stays null and a slice (e.g. Morning) is chosen. In
`WindowSelection.datedWindow` (`window_choice.dart:213-236`)
`(defaultStart, defaultEnd)` comes from `oneOffWindow(now)`, which caps `end`
at today or tomorrow at `slice.to`. The return substitutes only the start:
`(at(startDate, from), defaultEnd)`.

With now = 2026-09-08 15:00, slice = Morning, startDate = 2026-09-15,
dueDate = null the result is (2026-09-15 06:00, 2026-09-09 12:00) — end six
days before start. `reconcileAll` keeps the row `pending` while
`now < start`; the moment start is reached `phaseOf` sees end in the past
and returns `expired`, so the expiry sweep flips the task to missed the
instant it becomes active.

**Fix:** when `startDate` is set and `dueDate` is null, anchor the default
end to `startDate` (i.e. `at(startDate, slice.to)`, or the day after for a
rolled window), and assert/clamp `end >= start` before persisting.

### 5. Overflow view picked from More while on Settings/Stats is dropped (normal)

`onDestinationSelected` (`home_shell.dart:137-157`) opens the More sheet
(line 148) without clearing `_onSettings` / `_onStats`. The sheet's tile
`onTap` (lines 252-255) only does `setState(() => _selectedView = offset + i)`.
If the user is on Settings or Stats and taps More → a view, the flags stay
true, so `build` (lines 299-303) keeps rendering `SettingsScreen` /
`StatsScreen` and the nav bar (line 132) keeps highlighting that tab. The
chosen view is silently ignored. Requires more than four views (the More slot
only exists with overflow), which is exactly the population that uses it.

**Fix:** set `_onSettings = false; _onStats = false;` alongside the
`_selectedView` update in the sheet's `onTap`, or route the tap through the
same code path as a direct view-slot selection.

### 6. Detail sheet Column has no scroll wrapper (normal)

`_TaskDetailSheet.build()` (`task_detail_sheet.dart:325-533`) returns
`Padding → SafeArea(top: false) → Column(mainAxisSize: MainAxisSize.min, …)`
with up to ~20 optional children (name field, Save, mark-done-anyway, reopen,
stats row, reminders header, `ReminderEditor`, lens picker, two window date
tiles, history, series window, edit repeat, paused switch, delete, delete
series). The sheet is opened with `isScrollControlled: true` (lines 30-35),
so content taller than the viewport — a habit with stats + reminders + lens
picker on a small, split-screen or landscape device, plus keyboard
`viewInsets.bottom + 16` padding — produces a RenderFlex overflow and clipped
delete buttons. The sibling `_CreateTaskSheet` already wraps its Column in
`SingleChildScrollView`.

**Fix:** wrap the Column in `SingleChildScrollView` the same way.

### 7. Hardcoded English Android channel name/description (nit)

`notification_scheduler.dart:32-41` hardcodes `'Reminders'` (channel name)
and `channelDescription: 'Task reminders'` in a `const
AndroidNotificationDetails`. Android shows both in system Settings › Apps ›
Checkfuchs › Notifications and in per-channel DND controls, so de/fr/it
users see English there. Violates the CLAUDE.md "no hardcoded user-facing
strings" rule.

**Fix:** resolve both from `AppLocalizations` before the first
`zonedSchedule` (drop the `const`), and recreate the channel via
`AndroidFlutterLocalNotificationsPlugin.createNotificationChannel()` on
locale change since Android caches channel metadata.

### 8. Two sheets omit `isScrollControlled: true` (nit)

`_showStructureSheet` (`home_shell.dart:199`) and `_showMoreViews`
(`home_shell.dart:241`) pass only `showDragHandle: true`, so they default to
Flutter's half-screen cap, against the CLAUDE.md sheet rule.
`_showMoreViews` uses `ListView(shrinkWrap: true)` for the overflow list, so
a user with many extra views gets a clipped sheet; both misbehave once a
soft keyboard or bottom inset appears.

**Fix:** pass `isScrollControlled: true` like the other sheets in this file
family.

### 1. Vacation delete fires on a single tap with no confirmation or undo (normal)

`vacation_screen.dart:52-68` wires the trailing `IconButton` straight to
`taskRepositoryProvider.deleteVacation(v.id)` followed by `reconcileAll(...)`.
There is no `AlertDialog`, no `SnackBar` with Undo and no other guard. A
stray tap while scrolling the list permanently drops a planned holiday
window and the user has to re-pick the whole date range.

Every other destructive path added by this PR does confirm:
`library_screens.dart:406-443` (`_DeleteTile` for view/lens) and the
Delete-all-data row in `settings_screen.dart` both go through an
`AlertDialog` with Cancel → Confirm.

**Fix:** gate the delete behind the same Cancel → Confirm `AlertDialog`, or
show a `SnackBar` with an Undo action that re-inserts the vacation.

### 2. Delete all data splits wipe and seed across two transactions (normal)

`settings_screen.dart:279-282` runs
`await db.transaction(() => wipeContent(db));` and then
`await ref.read(viewRepositoryProvider).seedDefaults();` — a second,
separate `db.transaction` (`view_repository.dart:133`) — with no try/catch.
The success snackbar follows on the next line.

If `seedDefaults()` throws (drift integrity error, storage failure, the
widget scope disposed mid-flight) the wipe has already committed but the
required default View/Lens is absent. The async exception is swallowed by
Flutter's event handler, so the user sees no error and no completion
feedback, and Home renders the empty state until the next cold launch (where
`home_shell._startup` re-runs `seedDefaults`).

`debug_section.dart:164-168` (`_resetToIntro`) has the same shape:
`wipeContent` → `seedDefaults()` → `resetOnboarding()` → `runFirstLaunch()`
chained without isolation, so a failure in the middle strands the user in an
empty database without ever entering the intro flow.

**Fix:** run wipe + seed inside one `db.transaction`, wrap the whole action
in try/catch, and surface a failure snackbar instead of the success one.

### 3. Vacation ListView has no bottom padding (nit)

`vacation_screen.dart:44-71` builds `ListView(children: [...])` with no
`padding:`, while the Scaffold mounts a `FloatingActionButton.extended`
(line 76). On a 3-button navigation bar — the exact case the CLAUDE.md
pushed-screen rule covers — the last row draws under the nav bar and the
extended FAB overlaps the bottom tile's trailing delete icon until the user
overscrolls. Every sibling scrollable in this PR (`view_edit_screen.dart:54`,
`stats_screen.dart:94`, `task_history_screen.dart:52`, library screens)
uses `EdgeInsets.only(bottom: 24 + MediaQuery.paddingOf(context).bottom)`.

**Fix:** add the same bottom padding, plus extra room for the FAB height.

### 4. Theme picker title reuses the section-header key (nit)

`settings_screen.dart:33` renders `FuchsbauSectionHeader(l10n.appearanceSection)`
and line 38 sets the theme `FuchsbauChoicePicker`'s `title:` to the same
`l10n.appearanceSection` (`app_en.arb:216`). The row reads
"Appearance — System" directly under the uppercase "APPEARANCE" header,
while the neighbouring rows correctly say "App language" and "Typeface".
Same duplication in de/fr/it ("Darstellung", "Apparence", "Aspetto").

**Fix:** add a distinct key (e.g. `themePickerTitle` = "Theme") to
`app_en.arb` and mirror it into the three other arb files.

### 5. `colorScheme.error` used beyond the sanctioned Delete (nit)

`DESIGN_SYSTEM.md:102-103` §3.4 reserves error red as "the one sanctioned
alarm-red use" for the task-detail sheet's Delete, and CLAUDE.md restates it
("never red — red is destruction-only"). This PR paints it on four more
surfaces: the view/lens `_DeleteTile` icon + title and its dialog confirm
button (`view_edit_screen.dart:425-426, 440`), the Delete-all-data row and
confirm button in `settings_screen.dart`, the vacation delete icon in
`vacation_screen.dart`, and the reset label in `debug_section.dart`.

**Fix:** either drop the error tint from these secondary destructive rows
(uncoloured row + confirm dialog is enough), or broaden the rule in
`DESIGN_SYSTEM.md` §3.4 — CLAUDE.md requires the doc update when a new
pattern is introduced.

### 6. Duplicated file-private stream providers (nit)

An identical `_allLensesProvider =
StreamProvider.autoDispose<List<LensRow>>((ref) =>
ref.watch(viewRepositoryProvider).watchAllLenses())` exists in both
`library_screens.dart:24-26` and `view_edit_screen.dart:111-113`. The
all-tasks stream is wrapped three times: `tasksProvider` in
`providers.dart`, `_tasksProvider` in `stats_screen.dart:16` and
`_allTasksProvider` in `library_screens.dart:20`.

Each screen that watches one of these opens its own drift subscription, so
navigating All lenses ↔ Lens edit ↔ Stats ↔ History runs the same query
several times in parallel.

**Fix:** hoist one shared `allLensesProvider` into `providers.dart` and
reuse the existing `tasksProvider` instead of the file-private copies.

### 7. `_DayMarkPainter.shouldRepaint` compares 3 of 6 colours (nit)

`_DayMarkPainter` (`stats_screen.dart:217-287`) stores six theme-derived
colours (`done, onDone, skipped, missed, open, none`) and uses all six in
`paint()`, but `shouldRepaint` (lines 285-286) compares only `mark`, `done`
and `none`. Because `skipped`/`missed` come from `FuchsbauStatusColors`
rather than the `ColorScheme`, a status-colour change that leaves
`scheme.tertiary` / `outlineVariant` untouched keeps the cached paint in the
Week / Heatmap / Streaks tiles, so the taupe-missed and grey-skipped intent
from the design system is rendered stale.

**Fix:** compare every colour field in `shouldRepaint`.
